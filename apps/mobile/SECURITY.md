# Security scope and release gates

## Current trust boundary

Native onboarding offers create, restore and watch-only choices. The native host uses the shared software keyring for creation/import, unlock, prepared signing and seed backup. Runtime crypto/storage checks and session capabilities are mandatory; UI visibility is never an authorization boundary. Saved EVM registrations share one native-currency/ERC20 transfer path, with explicit network management and account-scoped assets. Account creation, selection, rename and eligible removal use complete persisted SDK account maps in one 4 MiB wallet-bound document. Add account delegates to the existing SDK gap-reuse policy; native IDs preserve its nonnegative safe-integer range. Ordinary unlock restores persisted records without rederiving or reimporting the map. The host binds the reviewed envelope and acknowledges the common profile/chain/sender signed-record store before submission; typed aliases share pending ownership and explicit replay uses the retained original bytes. Hardware signing, NFTs, Syscoin assets and dapp signing still need implementation/qualification. Full feature equivalence remains incomplete. Live testnet sends, physical-device behavior and signed release artifacts remain separate gates. The preview has no authority and stays isolated from wallet state.

Every valid saved EVM registration uses the same standard RPC and shared SDK fee/signing flow. Canonical receipt inclusion confirms an ordinary transfer; no network-specific depth or L1-settlement gate applies. Later reorg observations can revise status. Nonce consumption alone never establishes success or a replacement identity. Account/network/endpoint/revision checks, reviewed exact amounts, fresh authorization, durable common signed-record acknowledgement before broadcast and explicit identical-byte retries remain required.

A native watch-only account may persist public addresses in platform protected storage. That does not establish a secure vault implementation. Public addresses and their association with this device still deserve privacy protection. Network requests disclose queried addresses to the configured service; never add an analytics, crash-reporting or address-enrichment service without a separate product/privacy decision.

Public UTXO watching accepts supported SYS/BTC addresses, public extended keys and descriptors. Public-input validation and derivation reuse the extension/SDK; balances use the existing SyscoinJS Blockbook account query, including backend receive/change discovery. The configured mainnet indexer must match coin, network and genesis before receiving an identifier. Confirmed balance and signed pending change remain separate. Receive projects the initial address. Activity uses the same shared Blockbook account read and amount helpers as the extension, including indexed receive/change history for saved account keys/descriptors and address-only history for address records. The canonical identifier stays inside the authority; before/after storage checks and generation-bound owned cancellation protect publication. UTXO custody and SPT transfers/quantities are not implemented. A public account identifier reveals more of a wallet's history to the provider than a single address. Native requests use the owned no-redirect HTTP port. Source/browser tests do not establish device or deployed-provider behavior.

Native wallet HTTP uses an explicitly composed Expo fetch transport. It sends the captured string URL without React Native Request cache rewriting and requests native redirect rejection and omitted credentials before dispatch. Cache-Control and Pragma request no caching; unsupported RequestInit cache/referrerPolicy options are not treated as native guarantees. Each reader aborts its owned controller on completion or failure as well as lifecycle cancellation. Response limits bound consumed/parsed data, not all bytes that native networking may allocate or receive before cancellation. Device HTTP qualification remains separate from source and mocked-bridge tests.

Native custody uses an application-private SQLCipher database with a random device key in SecureStore, in addition to the SDK's password-encrypted records. A native directory adapter excludes the database from OS backups and rejects unexpected file types. Its lease admits one wallet owner within the current application process; cross-process exclusion is not established. Atomic record creation and wallet-bound backup receipts are mandatory. A missing key, a missing database after completed provisioning, corruption or a failed/ambiguous commit never authorizes erasure or replacement. SecureStore accessibility is not biometric authorization. Device compromise and an unlocked application remain outside the protection promised by database encryption.

PBKDF2/HKDF/AES-GCM are provided by narrow native key handles using CryptoKit/CommonCrypto on iOS and JCA/Bouncy Castle KDFs on Android. QuickCrypto supplies Node compatibility for SDK dependencies, not vault AES-GCM authentication classification. Production KDF parameters are unchanged. Only typed native authentication failures map to `OperationError`. Startup known-answer checks are capability checks, not an independent cryptographic audit.

Every native wallet session is revoked on background/inactive state and Android focus loss. Configurable foreground idle locking adds separate native/watch policies (default five minutes; Off or 5–120 minutes) without relaxing that rule. Native timeout increases and Off require scoped fresh password authentication through the existing throttle. Expiry is checked before input renewal and in native/public authority guards; a timer callback alone does not authorize continued use. Settings read failures retain bytes and block account opening; no native memory fallback or destructive repair is supplied. Foreground clock/input behavior, exact visual clearing during a stalled JavaScript thread and permanently malformed preference recovery remain qualification gates. Capture and app-switcher protection are requested before custody initialization and retained for the process lifetime. These APIs still require physical-device verification. Recovery words never enter public snapshots or the clipboard; JavaScript strings and keyboard memory cannot be guaranteed to be zeroized. Release builds remove console calls. No notification registration exists yet; adding it requires an explicit privacy design and must not grant custody authority.

The native development Security & backups screen reuses the seed-backup flow and can reveal the selected HD or imported EVM account's private key after fresh password authentication and confirmed seed backup. Secret exports use the same persistent authentication throttle as unlock and backup. The runtime single-flight gate also serializes them with signing. It binds the captured account kind/ID, catalogue revision and network registration, loads the authenticated persisted SDK records, and verifies that the returned scalar derives the selected address before presenting it. A network or account change, Hide, Back, unmount or lifecycle lock invalidates the presentation. The account key is independent of the selected EVM network and is not a wallet-wide backup. There is no private-key clipboard or share action. Matching-phrase password recovery is separate from destructive wallet removal and does not introduce a new account-export file format. Physical keyboard, screen privacy and native lifecycle qualification remain pending; JavaScript secret strings cannot be promised zeroized.

Native EVM import accepts a canonical 32-byte scalar after full-address review, backup acknowledgement and fresh password authentication. The shared imported-recovery helper and installed SDK AEAD create a seed-profile-bound encrypted recovery copy. That copy, the SDK's password-encrypted imported record, metadata and selection are acknowledged in the same account-document commit. Cold unlock uses the persisted SDK record; it does not decrypt and reimport every recovery copy. Recovery alone stages rewrapping with the actual SDK and verifies public identities. Envelopes and SDK ciphertext never enter public snapshots or watch storage. Unknown/corrupt required copies and uncertain writes fail closed without discarding data. The phrase can recover an imported key only with its retained copy or independent backup; it cannot derive a lost independent key.

Normal transfer confirmation and exact-byte retry use the current unlocked custody session and explicit review consent. They do not accept, cache or re-check a wallet password. The shared SDK signer uses its captured session guard; the mobile runtime binds the approved immutable envelope and rejects stale, locked or quarantined authority. Seed/private-key exports and sensitive account changes retain fresh password authentication.

Operation identity includes account, network, endpoint and a session/generation value. Returning from A to B to A is not the same authority context. Locking, backgrounding, account changes and network changes must invalidate pending work. A late network result cannot overwrite a newer context. Failed reads and unavailable balances must remain distinct from a valid zero or an absent account.

## Required before accepting wallet secrets

1. **One authoritative wallet.** Adapt the extension's tested operations behind explicit native interfaces. UI state is a projection, not authorization. Do not expose keyring records or generic method traversal across a bridge. Untrusted dapp content must not share a privileged wallet context.
2. **Native durable vault.** Preserve the shared keyring's password-encrypted vault envelope and recovery semantics. The native initial-install transaction creates the logical `vault` and `vault-keys`, complete account document and authenticated identity/root together after validating an empty snapshot across all four domains. The SQLCipher adapter acknowledges commit and readback; SDK `set`, `deleteItem` and later account CAS operations also require acknowledgement. A sequence of independent writes is insufficient. Keep unsupported records intact and fail closed. Use an appropriate encrypted transactional store for large vault data; protected key/value storage is not a substitute for that store.
3. **Key access and backup policy.** Define native wrapping-key access, biometric invalidation, device migration, reinstall, OS backup exclusions, password fallback and deliberate export behavior. Biometrics do not replace recovery. A seed alone does not recreate independent imported keys, passkeys or randomly generated private notes. Retained seed-profile-encrypted imported copies and note ciphertext are preserved and authenticated during supported recovery; absent copies cannot be invented. Never silently discard unsupported records.
4. **Lifecycle and interruption.** Test process termination at every creation, commit and recovery boundary. Reconcile interrupted writes before onboarding or rehydration. Test inaccessible key storage, storage exhaustion, successful writes with lost acknowledgments, failed deletion and resumed stale work. A read error must not authorize overwriting a vault.
5. **Secret lifetime and native privacy.** Keep secrets out of Redux, public snapshots, logs, telemetry, clipboard by default, app-switcher snapshots and untrusted web content. Verify secure input, screenshot/background behavior, keyboard/autofill handling and accessibility on actual supported devices. UI PIN dots are not authentication or brute-force protection.

## Required before transactions

- Use exact integer amounts and independent network identity checks. Show asset, complete recipient, account, network, amount and maximum fee before explicit confirmation. Invalidate review if its context or material transaction data changes.
- Persist the necessary intent/reservation before crossing a submission boundary. A timeout or process kill may mean broadcast acceptance is unknown. Reconcile using transaction/status evidence; never automatically retry a potentially accepted transfer.
- Qualify one native testnet transfer end to end before expanding support. EVM and UTXO/PSBT need separate acceptance. Test cancellation, duplicate taps, fee changes, insufficient funds, wrong chains, malformed responses and A-B-A races.
- Add dapp approvals, hardware transport, passkeys, smart accounts and private-note/prover operations only behind their own validated capabilities and threat models. Chain discovery is not proof that a feature works on that chain.

## Device and release qualification

Build and inspect signed release artifacts for both platforms. Test supported physical iOS and Android devices, including the slowest supported hardware, with cold start, unlock latency, large state, long histories, offline/slow RPC, background/resume and memory pressure. Verify accessibility, text scaling, safe areas, software keyboards and native back gestures. Validate transport security and release permissions against actual binaries.

Source review, unit tests, a browser preview, prior extension QA, the attached PDF and the video do not establish these properties. Keep a release checklist with exact commit, OS/device, build configuration, observed result and unresolved limitations. Do not describe this foundation as production-ready until the applicable gates have evidence.

## Native startup import order

The native entry registers a minimal loading shell, qualifies and installs native
crypto, then evaluates the application graph. This order is a security boundary:
BIP39's noble dependency snapshots `globalThis.crypto` when its module loads.
The web entry uses its usual watch-only application startup. If native crypto
qualification fails, watch-only UI may load, while the memoized rejected native
gate continues to prohibit custody. No fallback RNG is installed.

The isolated native qualification entry obeys the same ordering and checks the
real generated mnemonic against entropy observed from the qualified native
provider. Node ordering probes reproduce both the stale import failure and the
ordered success using the installed BIP39/noble browser module; those probes do
not replace native simulator/device qualification.
