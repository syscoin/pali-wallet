# Security scope and release gates

## Current trust boundary

Native onboarding offers create, restore and watch-only choices. The native host uses the shared software keyring for creation/import, unlock, prepared signing and seed backup. Runtime crypto/storage checks and session capabilities are mandatory; UI visibility is never an authorization boundary. Saved EVM registrations share one native-currency/ERC20 transfer path, with explicit network management and account-scoped assets. Account creation, selection, rename and eligible removal use complete persisted SDK account maps in one 4 MiB wallet-bound document. Add account delegates to the existing SDK gap-reuse policy; native IDs preserve its nonnegative safe-integer range. Ordinary unlock restores persisted records without rederiving or reimporting the map. The host binds the reviewed envelope and acknowledges the common profile/chain/sender signed-record store before submission; typed aliases share pending ownership and explicit replay uses the retained original bytes. Native hardware, NFT, Syscoin-asset and dapp transaction surfaces exist behind their respective capability and approval checks. Implementation does not establish physical-device or full end-to-end qualification. Full feature equivalence remains incomplete. Live testnet sends, physical-device behavior and signed release artifacts remain separate gates. The preview has no authority and stays isolated from wallet state.

Every valid saved EVM registration uses the same standard RPC and shared SDK fee/signing flow. Canonical receipt inclusion confirms an ordinary transfer; no network-specific depth or L1-settlement gate applies. Later reorg observations can revise status. Nonce consumption alone never establishes success or a replacement identity. Account/network/endpoint/revision checks, reviewed exact amounts, fresh authorization, durable common signed-record acknowledgement before broadcast and explicit identical-byte retries remain required.

A native watch-only account may persist public addresses in platform protected storage. That does not establish a secure vault implementation. Public addresses and their association with this device still deserve privacy protection. Network requests disclose queried addresses to the configured service; never add an analytics, crash-reporting or address-enrichment service without a separate product/privacy decision.

Public UTXO watching accepts supported addresses, public extended keys and descriptors on the shared enabled defaults. It also accepts custom endpoints for SDK-recognized UTXO coins after first-use identity verification. Public-input validation and derivation reuse the extension/SDK; balances use the existing SyscoinJS Blockbook account query, including backend receive/change discovery. The selected indexer must match the captured coin, network and genesis on same-origin reads before receiving an identifier. Confirmed balance and signed pending change remain separate. Receive projects the initial address. Activity uses the same shared Blockbook account read and amount helpers as the extension, including indexed receive/change history for saved account keys/descriptors and address-only history for address records. The canonical identifier stays inside the authority; before/after storage checks and generation-bound owned cancellation protect publication. Software HD and imported-WIF custody can send native coins on the shared enabled defaults through the SDK quote/signing path and common durable UTXO submission. Indexed SPT quantities use shared exact interpretation. SPT transfers, hardware routes and custom UTXO custody have separate capability and qualification requirements. A public account identifier reveals more of a wallet's history to the provider than a single address. Native requests use the owned no-redirect HTTP port. Source/browser tests do not establish device or deployed-provider behavior.

Native wallet HTTP uses an explicitly composed Expo fetch transport. It sends the captured string URL without React Native Request cache rewriting and requests native redirect rejection and omitted credentials before dispatch. Cache-Control and Pragma request no caching; unsupported RequestInit cache/referrerPolicy options are not treated as native guarantees. Each reader aborts its owned controller on completion or failure as well as lifecycle cancellation. Response limits bound consumed/parsed data, not all bytes that native networking may allocate or receive before cancellation. Device HTTP qualification remains separate from source and mocked-bridge tests.

Native custody uses an application-private SQLCipher database with a random device key in SecureStore. The shared SDK still encrypts its records, but the native host supplies a random device-protected secret rather than a user-entered password. The six-digit Pali PIN authorizes access; it is not the SDK encryption key. Its verifier is bound to the installation, wallet and enrollment using a device-protected random pepper and salt, with persistently recorded attempts before verification. A copied database alone must not provide an offline PIN verifier without that protected pepper. A native directory adapter excludes the database from OS backups and rejects unexpected file types. Its lease admits one wallet owner within the current application process; cross-process exclusion is not established. Atomic record creation and wallet-bound backup receipts are mandatory. A missing key, a missing database after completed provisioning, corruption or a failed/ambiguous commit never authorizes erasure or replacement. The database key's SecureStore accessibility does not grant biometric authorization. Device compromise and an unlocked application remain outside the protection promised by database encryption.

PBKDF2/HKDF/AES-GCM are provided by narrow native key handles using CryptoKit/CommonCrypto on iOS and JCA/Bouncy Castle KDFs on Android. QuickCrypto supplies Node compatibility for SDK dependencies, not vault AES-GCM authentication classification. Production KDF parameters are unchanged. Only typed native authentication failures map to `OperationError`. Startup known-answer checks are capability checks, not an independent cryptographic audit.

Every native wallet session is revoked on background/inactive state and Android focus loss. Configurable foreground idle locking adds separate native/watch policies (default five minutes; Off or 5–120 minutes) without relaxing that rule. Native timeout increases and Off require scoped fresh PIN or enabled biometric authorization through the persistent throttle. Expiry is checked before input renewal and in native/public authority guards; a timer callback alone does not authorize continued use. Settings read failures retain bytes and block account opening; no native memory fallback or destructive repair is supplied. Foreground clock/input behavior, exact visual clearing during a stalled JavaScript thread and permanently malformed preference recovery remain qualification gates. Capture and app-switcher protection are requested before custody initialization and retained for the process lifetime. These APIs still require physical-device verification. Recovery words never enter public snapshots or the clipboard; JavaScript strings and keyboard memory cannot be guaranteed to be zeroized. Release builds remove console calls. System watch notifications remain unwired. The separate #1265 native transport draft requires opt-in, exact-ID recovery and lifecycle/privacy qualification before activation and grants no custody authority.

The native development Security & backups screen reuses the seed-backup flow. It can reveal the selected HD/imported EVM private key or an imported UTXO WIF after fresh PIN or enabled biometric authorization and confirmed seed backup. Secret exports use the same persistent authentication throttle as unlock and backup. The runtime single-flight gate also serializes them with signing. It binds the captured account kind/ID, catalogue revision and network registration, loads the authenticated persisted SDK records, and verifies that the returned key derives the selected address before presenting it. WIF reveal also shows its canonical network and script type. A network or account change, Hide, Back, unmount or lifecycle lock invalidates the presentation. An EVM account key is independent of the selected EVM network. A WIF export is bound to its displayed network and script type. Neither export is a wallet-wide backup. There is no private-key clipboard or share action. Matching-phrase PIN recovery is separate from destructive wallet removal and does not introduce a new account-export file format. Physical keyboard, screen privacy and native lifecycle qualification remain pending; JavaScript secret strings cannot be promised zeroized.

Native EVM import accepts a canonical 32-byte scalar after full-address review, backup acknowledgement and fresh PIN or enabled biometric authorization. The shared imported-recovery helper and installed SDK AEAD create a seed-profile-bound encrypted recovery copy. That copy, the SDK's password-encrypted imported record, metadata and selection are acknowledged in the same account-document commit. Cold unlock uses the persisted SDK record; it does not decrypt and reimport every recovery copy. Recovery alone stages rewrapping with the actual SDK and verifies public identities. Envelopes and SDK ciphertext never enter public snapshots or watch storage. Unknown/corrupt required copies and uncertain writes fail closed without discarding data. The phrase can recover an imported key only with its retained copy or independent backup; it cannot derive a lost independent key.

Optional native biometric enrollment uses the platform-protected credential adapter, authenticated write/readback and revocation. The Pali PIN is the fallback; an OS device passcode is a separate credential. Capability-specific Face ID, Touch ID or biometric wording does not itself prove authentication: the protected credential result does. A result returned while the app lacks foreground/focus is discarded. Enrollment changes, device credential invalidation and physical-device behavior remain release gates. Mobile does not use a WebAuthn passkey to unlock this local vault; optional extension passkey unlock is a separate host feature.

Saved pending EVM cancellation is implemented for eligible type-0/type-2 transactions from the selected HD/imported payer. It uses authenticated original bytes and the original nonce, rechecks the live pending transaction and payer state, and preserves durable evidence before submission. It is a replacement attempt whose result must be observed. Speed Up and cancellation retain their original-nonce and explicit-review requirements.

The native host selects the shared SDK operation-lifetime policy. Opening the wallet retains public account context, not reusable software signing authority. Public preparation finishes before a one-use authorization bound to the account, network and exact reviewed transaction can release the software secret. The SDK retires its owned secret buffers on completion, failure or cancellation. Public transaction journals retain only explicit domain-limited record capabilities, so ordinary saved-byte inspection and retry do not reload the mnemonic. Private-note reconciliation needs separate explicit authorization for its note-only capability. The extension intentionally retains its existing session-unlock policy. Neither policy promises erasure of every JavaScript string or cryptographic-library temporary.

Operation identity includes account, network, endpoint and a session/generation value. Returning from A to B to A is not the same authority context. Locking, backgrounding, account changes and network changes must invalidate pending work. A late network result cannot overwrite a newer context. Failed reads and unavailable balances must remain distinct from a valid zero or an absent account.

## Required before accepting wallet secrets

1. **One authoritative wallet.** Adapt the extension's tested operations behind explicit native interfaces. UI state is a projection, not authorization. Do not expose keyring records or generic method traversal across a bridge. Untrusted dapp content must not share a privileged wallet context.
2. **Native durable vault.** Preserve the shared keyring's password-encrypted vault envelope and recovery semantics. The native initial-install transaction creates the logical `vault` and `vault-keys`, complete account document and authenticated identity/root together after validating an empty snapshot across all four domains. The SQLCipher adapter acknowledges commit and readback; SDK `set`, `deleteItem` and later account CAS operations also require acknowledgement. A sequence of independent writes is insufficient. Keep unsupported records intact and fail closed. Use an appropriate encrypted transactional store for large vault data; protected key/value storage is not a substitute for that store.
3. **Key access and backup policy.** Define native wrapping-key access, biometric invalidation, device migration, reinstall, OS backup exclusions, PIN fallback and deliberate export behavior. Biometrics do not replace recovery. A seed alone does not recreate independent imported keys, passkeys or randomly generated private notes. Retained seed-profile-encrypted imported copies and note ciphertext are preserved and authenticated during supported recovery; absent copies cannot be invented. Never silently discard unsupported records.
4. **Lifecycle and interruption.** Test process termination at every creation, commit and recovery boundary. Reconcile interrupted writes before onboarding or rehydration. Test inaccessible key storage, storage exhaustion, successful writes with lost acknowledgments, failed deletion and resumed stale work. A read error must not authorize overwriting a vault.
5. **Secret lifetime and native privacy.** Keep secrets out of Redux, public snapshots, logs, telemetry, clipboard by default, app-switcher snapshots and untrusted web content. Verify secure input, screenshot/background behavior, keyboard/autofill handling and accessibility on actual supported devices. UI PIN dots are not authentication or brute-force protection.

## Required before transactions

- Use exact integer amounts and independent network identity checks. Show asset, complete recipient, account, network, amount and maximum fee before explicit confirmation. Invalidate review if its context or material transaction data changes.
- Persist the necessary intent/reservation before crossing a submission boundary. A timeout or process kill may mean broadcast acceptance is unknown. Reconcile using transaction/status evidence; never automatically retry a potentially accepted transfer.
- Qualify one native testnet transfer end to end before expanding support. EVM and UTXO/PSBT need separate acceptance. Test cancellation, duplicate taps, fee changes, insufficient funds, wrong chains, malformed responses and A-B-A races.
- Add dapp approvals, hardware transport, passkeys, smart accounts and private-note/prover operations only behind their own validated capabilities and threat models. Chain discovery is not proof that a feature works on that chain.

## Device and release qualification

Build and inspect signed release artifacts for both platforms. Test supported physical iOS and Android devices, including the slowest supported hardware, with cold start, unlock latency, large state, long histories, offline/slow RPC, background/resume and memory pressure. Verify accessibility, text scaling, safe areas, software keyboards and native back gestures. Validate transport security and release permissions against actual binaries.

Source review, unit tests, a browser preview, prior extension QA, the attached PDF and the video do not establish these properties. Keep a release checklist with exact commit, OS/device, build configuration, observed result and unresolved limitations. Do not describe this foundation as production-ready until the applicable gates have evidence.

## Native startup import order

The native entry registers a minimal loading shell, qualifies and installs native
crypto, then evaluates the application graph. This order is a security boundary:
BIP39's noble dependency snapshots `globalThis.crypto` when its module loads.
The web entry uses its usual watch-only application startup. If native crypto
qualification fails, watch-only UI may load, while the memoized rejected native
gate continues to prohibit custody. No fallback RNG is installed.

The isolated native qualification entry obeys the same ordering and checks the
real generated mnemonic against entropy observed from the qualified native
provider. Node ordering probes reproduce both the stale import failure and the
ordered success using the installed BIP39/noble browser module; those probes do
not replace native simulator/device qualification.
