# Pali mobile: extension feature-equivalence matrix

Original design basis: November 2, 2026, extension source **`4470e54e8777cca2a4fe7c712409f60eeb4fa401`**. The handoff reference `88cc9c9a8959b5dccc7ff43f136d60203782918a` adds documentation, not wallet behavior. The detailed capability rows retain that design inventory, with the implemented note-bundle enhancement recorded below.

**Implementation coverage** describes the development source alongside this document. The [shared-core audit](../docs/shared-core-audit.md) records the extension reuse decisions. Historical native evidence below belongs only to its recorded revisions; source presence, a reviewed patch, or a signed test build does not qualify the current app.

**Target:** carry every supported extension user journey into mobile, preserving account/network restrictions, consent, errors and recovery semantics. The source implements only part of that target. A designed screen, an implemented controller and a native-qualified flow are three different statuses; none alone establishes a shipping release or complete feature equivalence.

Native custody's account map is bounded to 4 MiB, without the earlier 20-account/4095-index/monotonic/Restore policy. Public watch records independently retain their current 20-account/32 KiB bound. Common signed records retain up to 4,096 transactions within 16 MiB. At capacity, bounded automatic maintenance can remove completed nonce groups after fresh receipt, inclusion and finalized-state observations from the configured RPC, then retry the same signed bytes. Unresolved groups remain retained. New admission is refused if enough space cannot be reclaimed. Explicit activity reset removes the selected account/network tracking and nonce floor, invalidates outstanding work and keeps the configured RPC. Account removal does not erase signed records. The ordinary native unlock path restores persisted complete SDK maps rather than deriving/reimporting all accounts. Recovery is the separate shared staged rewrap path.

Primary implementation references are `src/custody/{keyringRuntime,walletCatalogue,recovery,networkContext,transfers,utxoSend}.ts`, `src/core/{utxoIdentifier,utxoBalanceReader,watchAccountCodec}.ts`, `src/activity/`, shared `source/wallet/{accountRecords,accountRecovery,evmSignedRecords,evmSignedReplay}.ts` and `source/shared/{evmExplorer,evmHistory}.ts`. The shell mounts only the active public tab; secret and approval screens remain separate. Native connection entry points are `src/screens/NativeConnections.tsx` and `src/connections/`; their operational qualification, dapp signing and hardware support remain open.

The stable tab order is **Wallet / Activity / Tools / Settings**. Connections is a destination inside Tools, not a fifth tab. Privacy, Smart account and Sentry also have contextual Wallet entries; these open the same Tools-owned screens. Child-flow names below are relative to those primary hubs. The tabs are a mobile organization choice, not existing extension navigation. Preserve the distinction between the selected account, selected network and a dapp's authorized account/network. Switching the displayed account cannot silently retarget an open approval.

## Reading the matrix

- **Extension evidence** identifies actual source paths and the scope visible there. Source presence does not establish universal network support or past device validation.
- **Mobile target** is the proposed screen or flow. All rows are in the equivalence target.
- **Qualification** names the work required before a live capability can be enabled. Common requirements apply to every row: accessible text/touch targets, safe-area and keyboard behavior, explicit loading/unavailable/error states, no stale-context commits, and real iOS/Android testing.

Paths are repository-relative. The route index is [source/routers/index.tsx](../../../source/routers/index.tsx); provider capability and request coverage are governed by [method-registry.ts](../../../source/scripts/Background/controllers/message-handler/method-registry.ts), not by the number of visible screens.

## Ordered remaining implementation slices

This is an engineering order, not a reduced parity target. Native qualification of existing flows continues in parallel.

1. **Shell expansion and settings:** extend the operational four-tab shell with localization, currency, support and the remaining Tools capabilities as their implementations land. Retain account/network and navigation state, accessible native input and safe unavailable states.
2. **Complete public watching:** qualify the implemented SDK extended-key/descriptor and Blockbook account-balance path, including account-wide receive/change history and custom watch-network identity checks. Reuse existing shared account behavior; do not introduce a mobile derivation/scanning engine. Optional alerts still need enrollment, delivery and privacy work.
3. **Recovery and security:** qualify full-record preserving recovery, idle/lifecycle locking and saved-data inventory on current native builds; qualify deliberate wallet removal and complete device-unlock wiring only after its native credential gates pass. Recovery must retain the actual encrypted imported/note/authenticator data and must not promise reconstruction from a phrase without those copies.
4. **EVM assets and transactions:** qualify the shared generic EVM path on representative chains and custom registrations, including exact-byte replay after interruption. Qualify implemented cancellation, Speed Up, queued sends and ERC-721/ERC-1155 transfers. Complete general token search and remaining asset coverage through the shared transaction engines.
5. **UTXO custody and hardware:** qualify native-coin send, MAX and the first ordinary SYSX allocation-send path, then add remaining SPT/RBF/Z-DAG flows through the same extension/SDK behavior. Public account watching does not establish UTXO signing. Native Ledger/Trezor discovery and signing require separate model/transport qualification.
6. **Connected apps:** add QR scanning and external-browser deep-link pairing, including cold/warm launch, unlock handoff and return-to-app behavior. Qualify the native session/grant/revocation draft with its configured project ID, then complete the message/transaction signing screens and full request/approval matrix. Origin, account, network and request identity remain distinct from the selected display context.
7. **Private notes:** qualify the implemented shared backup/restore with native storage/file access, then complete pool synchronization, note management, deposits and direct/relayed withdrawals with proof, interruption and uncertain-submission handling.
8. **Smart accounts and Sentry:** implement deployment/authenticators/composite policies and guardian recovery, then role-separated Sentry keys, collateral/link and operation/vote approvals. Guardian threshold 1 and composite signing thresholds remain separate policies.

## Equivalence acceptance and intentional boundaries

1. Each ID must have an implemented screen/entry or nonvisual protocol test, a tested backend capability, account/network/OS constraints, exact app revision, and failure/interruption evidence before it is marked complete. “Looks the same” and “TypeScript builds” are separate from this acceptance.
2. Test account classes independently: HD, imported signing key, watch-only address/extended key/descriptor, Ledger, Trezor, and smart account with each supported authenticator. Do not route them through a generic software-signing fallback. Preserve imported/private records even when their native operation is temporarily unavailable.
3. Test EVM, Syscoin UTXO and other registered UTXO networks separately. Default network discovery does not qualify assets, smart accounts, hardware, privacy or Sentry on every network.
4. Retain approval origin/account/network/request identity, generation checks, exact review data, rejection, timeout and unknown-broadcast states. App navigation, QR or external links may request a review but never authorize it.
5. Baseline does not supply a native dapp browser, native swap/bridge/staking product, cloud vault backup or mobile push service. Those are separate product additions; existing supported dapp calls, recovery-alert links and signing flows remain in scope.
6. Ledger model support and native Trezor transport need a separately maintained model/OS/app-version matrix. Current product names or an extension connection are not proof of mobile transport/signing support.
7. Ordering the work as custody -> transfers -> connections -> advanced modules is an implementation sequence, not permission to declare a reduced wallet “feature equivalent.” The target remains every row above, with honest unavailable states until its native gates pass.
8. Keep proposed additions separate from source parity: optional BIP39-passphrase intake, an ordinary standalone password-change screen, multi-guardian threshold editing, arbitrary executor/hook consent and arbitrary bundler/paymaster editors are not established by the original baseline UI. Whole-note encrypted backup/restore is implemented in both hosts and remains subject to native file/device qualification. Existing-wallet recovery can set a new password through its guarded matching-identity path. Infrastructure status/deployment uses configured contracts; native hardware transports need their own compatibility evidence.
