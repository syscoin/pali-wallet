# Pali mobile: extension feature-equivalence matrix

Design basis: November 2, 2026. Extension source: **`4470e54e8777cca2a4fe7c712409f60eeb4fa401`**. The source was read in this worktree; the handoff reference `88cc9c9a8959b5dccc7ff43f136d60203782918a` adds documentation, not wallet behavior. This is a design inventory and target, not a claim that mobile functionality is implemented or production-qualified.

Implementation note (manual ERC20 portfolio and Ethereum sends): W02 now has a native entry for contract import/review/confirmation, durable account-and-registration-scoped descriptors, exact balance observations, token details, Receive and removal from the local list. Ethereum ERC20 send reviews bind the token contract, recipient, units and separate ETH fee to a durable intent and signed bytes; other networks remain read/receive-only. Read failures and unknown balances remain distinct from zero. This is partial W02/T01 coverage: discovery/search, market information, NFT/SPT support and additional signing networks remain outstanding. Controller, SQLite and actual-component browser evidence does not establish physical-device qualification or complete W02/T01 parity.

Implementation note (Ethereum Activity): Ethereum HD accounts now have native direct-transaction/ERC20-event activity, bounded indexed paging, RPC-backed details, safe address-copy review and a bounded local terminal archive. Terminal records are archived before journal replacement or account removal. This is partial T03 coverage: internal ETH transfers, additional networks/account classes and replacements remain outstanding. Browser and controller evidence do not establish physical-device qualification or complete history coverage.

Implementation note (NEVM testnet native sends): fixed Syscoin NEVM Testnet chain 5700 now has native TSYS review, password-confirmed signing, per-chain journal/retry and a labelled 12-confirmation depth policy. ERC20 remains Ethereum-only; other new-chain sending remains disabled. Depth confirmation is not protocol finality or verified ChainLock evidence. This adds partial N01/T01 coverage; live endpoint/native-device qualification remains pending.

**Target:** carry every supported extension user journey into the mobile product, preserving account/network restrictions, review and consent, error handling, and recovery semantics. Layout and operating-system integration can change. An advanced feature awaiting native qualification stays in this matrix; it is not silently removed from the target.

**Actual mobile baseline:** The native development flow implements wallet creation/import, password unlock, seed backup, multiple seed-derived Ethereum accounts (create/select/rename/remove/restore), and per-account ETH portfolio, receive and send operations with an encrypted transaction journal. `apps/mobile/src/core/watchOnlyAuthority.ts` separately provides public EVM account watching without signing authority; the visual preview contains sample data. Full extension feature equivalence remains incomplete. An end-to-end native testnet transfer, physical-device behavior and signed release artifacts remain unqualified. The rows below are the broader target, not completed-capability claims.

## Navigation and screen organization

| Mobile location         | Contents and entry points                                                                                                                                                                                                                                                                                                    |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Wallet**              | Selected account and network, native balance/fiat state, Send and Receive, Tokens/NFTs, asset detail, and contextual Smart account / Privacy / Sentry entry cards where applicable. Account and network choosers are separate header sheets.                                                                                 |
| **Activity**            | Selected account/network history; transaction details; pending/replacement states; batch status. Preserve paging/filter/scroll position when returning from details or settings.                                                                                                                                             |
| **Tools**               | Primary hubs for Privacy, Smart account, Sentry and Connected apps. Connected apps contains sessions, permissions, connection details, new connection entry and trusted-site lookup. Incoming requests open an app-owned review flow above the current location. No permanently privileged embedded dapp browser is implied. |
| **Settings**            | Accounts, Networks, Security & backups, Language & currency, Advanced, Help & about. Advanced can link to tool-specific configuration, but the operational Privacy, Smart account and Sentry hubs live in Tools. Contextual shortcuts from Wallet open those same hubs.                                                      |
| **Before unlock**       | Welcome/create/import, password/unlock, seed backup/confirmation, recovery, storage failure/retry. No main navigation over exposed secrets.                                                                                                                                                                                  |
| **Global review flows** | Send, signing, permission/network changes, hardware confirmation and recovery: full-screen steps with account/network/origin context and a safe-area footer. Details open within the review without losing it.                                                                                                               |

The stable tab order is **Wallet / Activity / Tools / Settings**. Connections is a destination inside Tools, not a fifth tab. Privacy, Smart account and Sentry also have contextual Wallet entries; these open the same Tools-owned screens. Child-flow names below are relative to those primary hubs. The tabs are a mobile organization choice, not existing extension navigation. Preserve the distinction between the selected account, selected network and a dapp's authorized account/network. Switching the displayed account cannot silently retarget an open approval.

## Reading the matrix

- **Extension evidence** identifies actual source paths and the scope visible there. Source presence does not establish universal network support or past device validation.
- **Mobile target** is the proposed screen or flow. All rows are in the equivalence target.
- **Qualification** names the work required before a live capability can be enabled. Common requirements apply to every row: accessible text/touch targets, safe-area and keyboard behavior, explicit loading/unavailable/error states, no stale-context commits, and real iOS/Android testing.

Paths are repository-relative. The route index is [source/routers/index.tsx](../../../source/routers/index.tsx); provider capability and request coverage are governed by [method-registry.ts](../../../source/scripts/Background/controllers/message-handler/method-registry.ts), not by the number of visible screens.

## Equivalence acceptance and intentional boundaries

1. Each ID must have an implemented screen/entry or nonvisual protocol test, a tested backend capability, account/network/OS constraints, exact app revision, and failure/interruption evidence before it is marked complete. “Looks the same” and “TypeScript builds” are separate from this acceptance.
2. Test account classes independently: HD, imported signing key, watch-only address/extended key/descriptor, Ledger, Trezor, and smart account with each supported authenticator. Do not route them through a generic software-signing fallback. Preserve imported/private records even when their native operation is temporarily unavailable.
3. Test EVM, Syscoin UTXO and other registered UTXO networks separately. Default network discovery does not qualify assets, smart accounts, hardware, privacy or Sentry on every network.
4. Retain approval origin/account/network/request identity, generation checks, exact review data, rejection, timeout and unknown-broadcast states. App navigation, QR or external links may request a review but never authorize it.
5. Baseline does not supply a native dapp browser, native swap/bridge/staking product, cloud vault backup or mobile push service. Those are separate product additions; existing supported dapp calls, recovery-alert links and signing flows remain in scope.
6. Ledger model support and native Trezor transport need a separately maintained model/OS/app-version matrix. Current product names or an extension connection are not proof of mobile transport/signing support.
7. Ordering the work as custody -> transfers -> connections -> advanced modules is an implementation sequence, not permission to declare a reduced wallet “feature equivalent.” The target remains every row above, with honest unavailable states until its native gates pass.
8. Keep proposed additions separate from source parity: optional BIP39-passphrase intake, an ordinary standalone password-change screen, encrypted multi-note export files, multi-guardian threshold editing, arbitrary executor/hook consent and arbitrary bundler/paymaster editors are not established by this baseline UI. Existing-wallet recovery can set a new password through its guarded matching-identity path. Infrastructure status/deployment uses configured contracts; native hardware transports need their own compatibility evidence.
