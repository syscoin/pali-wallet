# Pali mobile: extension feature-equivalence matrix

Original design basis: November 2, 2026, extension source **`4470e54e8777cca2a4fe7c712409f60eeb4fa401`**. The handoff reference `88cc9c9a8959b5dccc7ff43f136d60203782918a` adds documentation, not wallet behavior. The detailed capability rows retain that design inventory, with the implemented note-bundle enhancement recorded below.

**Current implementation source basis: `6228217b837319dd3a2e1fdaf4324f7a4d1b5faa`**, reviewed November 4, 2026, before these prose updates. The operational shell extends the [public UTXO watch PR #1181](https://github.com/syscoin/pali-wallet/pull/1181) and [native HTTP qualification PR #1180](https://github.com/syscoin/pali-wallet/pull/1180) stack. Its unchanged code was restacked onto documentation head `a2fdcb7f432611e78783f250f8923d9320955937`. These documentation edits do not extend the reviewed runtime scope or establish a release.

**Target:** carry every supported extension user journey into mobile, preserving account/network restrictions, consent, errors and recovery semantics. The source implements only part of that target. A designed screen, an implemented controller and a native-qualified flow are three different statuses; none alone establishes a shipping release or complete feature equivalence.

Source tests and the synthetic browser fixture do not qualify deployed providers, native transport or physical-device use.

The shell reuses existing session owners and mounts only the active public tab. Authentication, seed/key presentation and approvals remain full-screen without tabs. Ethereum activity accepts both native account kinds; older descriptions of an HD-only scope are historical.

### Qualification boundary

- Prior [PR #1176](https://github.com/syscoin/pali-wallet/pull/1176) evidence verified offline Android HD-key reveal and custody/cold-restart behavior at that tested revision. It does not qualify later changes or live transfers.
- iOS Simulator native-crypto execution and the expected protected-storage refusal are limited evidence, with `custodyQualified: false`; they are not successful iOS custody or physical-iPhone qualification.
- [PR #1177](https://github.com/syscoin/pali-wallet/pull/1177) native artifacts are verified at head `9bf416401ab9c0120409d85b9b67bf9b70fd99e7`: Android import/generate create-and-restart cases cover imported account 1 signing, key reveal/clear and exact-byte retries on chains 1/5700/57057, retaining prior HD evidence with offline injected RPC and `networkCalls=0`. Its iOS result remains native crypto plus expected storage refusal only, not custody/restart qualification. This evidence belongs to that head, not the current source or physical/live execution. [PR #1180](https://github.com/syscoin/pali-wallet/pull/1180) artifacts at `dfa6e3c6876d858f69b97d6cd27eb077a86de7a0` additionally verify the loopback HTTP contract on Android and iOS; iOS custody remains refused. These results do not qualify physical-device networking or this shell’s native UI.
- Live RPC behavior, funded end-to-end transfers, physical-device privacy/keyboard/accessibility and signed release artifacts remain separate gates. Ordinary EVM confirmation uses a canonical receipt for all registrations, without L1-settlement or fixed-depth gates. Later refreshes may revise an observation after a reorg.

See [the native qualification contract](../qualification/README.md) for exact artifact requirements. No ledger row is fully native-qualified without its own revision-bound evidence.

Connected apps contains sessions, permissions, connection details, new connection entry and trusted-site lookup. Incoming requests open an app-owned review flow above the current location. | **Settings**            | Accounts, Networks, Security & backups, Language & currency, Advanced, Help & about. | **Before unlock**       | Welcome/create/import, password/unlock, seed backup/confirmation, recovery, storage failure/retry. No main navigation over exposed secrets.                                                                                                                                                                                  |
| **Global review flows** | Send, signing, permission/network changes, hardware confirmation and recovery: full-screen steps with account/network/origin context and a safe-area footer. Details open within the review without losing it.                                                                                                               |

The stable tab order is **Wallet / Activity / Tools / Settings**. Connections is a destination inside Tools, not a fifth tab. Privacy, Smart account and Sentry also have contextual Wallet entries; these open the same Tools-owned screens. Child-flow names below are relative to those primary hubs. The tabs are a mobile organization choice, not existing extension navigation. Preserve the distinction between the selected account, selected network and a dapp's authorized account/network. Switching the displayed account cannot silently retarget an open approval.

## Reading the matrix

- **Extension evidence** identifies actual source paths and the scope visible there. Source presence does not establish universal network support or past device validation.
- **Mobile target** is the proposed screen or flow. All rows are in the equivalence target.
- **Qualification** names the work required before a live capability can be enabled. Common requirements apply to every row: accessible text/touch targets, safe-area and keyboard behavior, explicit loading/unavailable/error states, no stale-context commits, and real iOS/Android testing.

Paths are repository-relative. The route index is [source/routers/index.tsx](../../../source/routers/index.tsx); provider capability and request coverage are governed by [method-registry.ts](../../../source/scripts/Background/controllers/message-handler/method-registry.ts), not by the number of visible screens.

## Ordered remaining implementation slices

This is an engineering order, not a reduced parity target. Native qualification of existing flows continues in parallel.

1. **Shell expansion and settings:** extend the operational four-tab shell with localization, currency, support and the remaining Tools capabilities as their implementations land. Retain account/network and navigation state, accessible native input and safe unavailable states.
2. **Complete public watching:** integrate shared BIP84 extended-key/descriptor support after its own review, then receive/change discovery and public history. Optional account alerts need separate enrollment, delivery and privacy work; polling is not a notification service.
3. **Recovery and security:** qualify the implemented matching-phrase password recovery and saved-data inventory; implement deliberate wallet removal, then configurable auto-lock and qualified biometric convenience. Preserve separate backups for imported keys, private notes and authenticators.
4. **EVM assets and transactions:** qualify additional networks individually; extend tokens/history, replacements and pending handling. Add NFT ownership/quantity and transfer flows; do not infer signing support from a displayed balance.
5. **UTXO custody and hardware:** add SYS/BTC account derivation/import, receive/change, fee/max/coin selection, PSBT review and durable signing/submission; add applicable SPT/RBF/Z-DAG behavior. Native Ledger/Trezor account discovery and signing need their own model/transport qualification.
6. **Connected apps:** implement native sessions, grants and revocation, then the full request/approval matrix. Origin, account, network and request identity remain distinct from the selected display context.
7. **Private notes:** connect shared backup/restore to native storage/file access, then pool synchronization, note management, deposits and direct/relayed withdrawals with proof, interruption and uncertain-submission handling.
8. **Smart accounts and Sentry:** implement deployment/authenticators/composite policies and guardian recovery, then role-separated Sentry keys, collateral/link and operation/vote approvals. Guardian threshold 1 and composite signing thresholds remain separate policies.

## Equivalence acceptance and intentional boundaries

1. Each ID must have an implemented screen/entry or nonvisual protocol test, a tested backend capability, account/network/OS constraints, exact app revision, and failure/interruption evidence before it is marked complete. “Looks the same” and “TypeScript builds” are separate from this acceptance.
2. Test account classes independently: HD, imported signing key, watch-only address/extended key/descriptor, Ledger, Trezor, and smart account with each supported authenticator. Do not route them through a generic software-signing fallback. Preserve imported/private records even when their native operation is temporarily unavailable.
3. Test EVM, Syscoin UTXO and other registered UTXO networks separately. Default network discovery does not qualify assets, smart accounts, hardware, privacy or Sentry on every network.
4. Retain approval origin/account/network/request identity, generation checks, exact review data, rejection, timeout and unknown-broadcast states. App navigation, QR or external links may request a review but never authorize it.
5. Baseline does not supply a native dapp browser, native swap/bridge/staking product, cloud vault backup or mobile push service. Those are separate product additions; existing supported dapp calls, recovery-alert links and signing flows remain in scope.
6. Ledger model support and native Trezor transport need a separately maintained model/OS/app-version matrix. Current product names or an extension connection are not proof of mobile transport/signing support.
7. Ordering the work as custody -> transfers -> connections -> advanced modules is an implementation sequence, not permission to declare a reduced wallet “feature equivalent.” The target remains every row above, with honest unavailable states until its native gates pass.
8. Keep proposed additions separate from source parity: optional BIP39-passphrase intake, an ordinary standalone password-change screen, multi-guardian threshold editing, arbitrary executor/hook consent and arbitrary bundler/paymaster editors are not established by the original baseline UI. Whole-note encrypted backup/restore is now an implemented shared/extension enhancement and remains a mobile integration requirement. Existing-wallet recovery can set a new password through its guarded matching-identity path. Infrastructure status/deployment uses configured contracts; native hardware transports need their own compatibility evidence.
