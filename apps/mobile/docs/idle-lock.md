# Foreground idle locking

The development flow provides **Settings → Auto-lock** for native wallets and watch accounts. Each mode has a separate device-local preference: a watch-only change cannot alter the native wallet timeout. Missing preferences use five minutes; valid choices are Off or whole minutes from 5 to 120. Off applies only while the app remains open. Background/inactive and Android focus loss still revoke the session, and no setting automatically unlocks it.

Native timeout increases and Off require fresh password authentication through the existing runtime authentication throttle and single-flight gate. Shortening a native timeout needs a current native owner; watch changes need a current watch owner. The native authority owns the entire scoped authentication/save operation, with no reusable authentication result and no SDK object exposed to the screen. Changing account, network, owner or screen, locking, backgrounding or expiry invalidates pending work. Known wrong-password failures still count when an in-flight KDF completes after cancellation, against the original storage pair.

The pure `source/shared/idleLockPolicy.ts` parser/evaluator contains no host APIs; existing extension runtime behavior is unchanged. Mobile `IdleLock` owns one timer and a session owner. Timers are wake-ups: expiry is also checked before user activity and at the native authority/runtime and public-authority guards. Touch, press, keyboard input and accessibility activation can renew a current session. Network results, renders, saves and asynchronous completions cannot. An expired interaction is rejected before it can renew the session. Timer functions retain their host receiver; replaced timers cannot affect a new owner. Monotonic and wall-clock samples are used conservatively, with invalid/backward samples causing revocation.

Native screen revocation clears transient password/recovery input and key/seed presentations, aborts owned work and calls the existing authority lock immediately. Pending authentication still drains, and late results cannot reopen the session. Transaction journals are preserved. Foreground creation/import/recovery/unlock forms are covered even when no wallet is unlocked. JavaScript strings are not promised zeroized, and a blocked JavaScript thread cannot promise exact physical screen blanking at the deadline. Native clock, input/accessibility, screen and lifecycle behavior remains a device qualification gate.

## Persistence and failure behavior

`pali.mobile.security-preferences.v1` is stored under a dedicated platform protected-storage service, outside the native vault and public-account record. Its exact bounded document is `{ version: 1, custodyIdleMinutes, watchIdleMinutes }`. It contains no credentials, account identifiers, endpoints or activity timestamps. Web uses ephemeral memory; native never falls back to memory when protected storage fails.

One repository serializes mode-specific writes using owner-bound immutable snapshots, exact raw read/compare/write/readback and token retirement. Changes preserve the other mode. Settings become effective only after acknowledged readback, and policy changes do not reset the last user-activity time. A shorter timeout can therefore lock immediately after a slow save. Failed/ambiguous writes revoke the affected session and require a successful reread; they are never replayed or compensated from stale data. A committed value may be discovered after an acknowledgement was lost.

Only an explicitly missing key uses defaults. Corrupt, oversized, unsupported or unreadable data is retained and blocks opening accounts and saving changes. The UI offers **Retry security settings**, never create/import/reset/delete as a remedy. There is no authorized repair flow for a permanently malformed preference record in this slice; safe recovery for that case is an unresolved product/qualification gate. Do not advise deleting wallet data.

## Evidence boundary

Focused policy/store/authority tests, a targeted real published-SDK authentication test and the actual App/native-session browser fixture cover the source contract. Browser storage, clocks and lifecycle events are synthetic and external requests are fenced. These do not establish physical-device timing, keyboard/autofill, screen protection, SecureStore interruption behavior or signed-release acceptance. Biometrics and altered background-lock policy remain separate work.
